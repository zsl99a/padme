## 维护原则

### 1. 触发沉淀的场景

- 第一次做某类机会时,把流程写下来。
- 踩坑并找到解决方案时,必须把经验沉淀为新规则(可能是新文件,也可能是补到已有规则的「踩坑记录」一节)。
- 发现某条规则与现实冲突时,先确认冲突,再修订规则并在 commit message 写明原因。

### 2. 沉淀格式

- 每条规则是一个独立 Markdown 文件,文件名 `NNN-短描述.md`。
- 头部必须有 YAML frontmatter:`type`、`status`(active/deprecated/draft)、`last_updated`。
- 正文按「目的 / 适用范围 / 具体规则 / 踩坑记录 / 变更日志」组织。
- 任何新规则必须在本 README 的「规则列表」登记。

### 3. 修订流程

1. 编辑规则文件。
2. 同步更新本 README。
3. 在文件的「变更日志」追加一行。
4. 提交(若用户授权),commit message 写明「规则:XXXX」。

### 4. 退役

规则被新规则替代或与现实严重脱节时:
- `status` 改为 `deprecated`。
- 顶部加一行「**已被 [NNN-...](./NNN-...) 替代**」。
- 不删除文件,保留历史。
