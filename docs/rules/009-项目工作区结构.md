# 009 - 项目工作区结构

## 目的

明确 `docs/` 与 `workflows/` 的职责分工,避免机会档案、可执行材料、跨工作流规则互相混杂。

## 适用范围

所有套利机会的档案编写与项目工作区搭建。

## 具体规则

### 1. 顶层结构

```
padme/
├── docs/                # 跨赚钱机会的公共层
│   ├── rules/           # 工作区所有规则(001-009 ...)
│   ├── opportunities/   # 机会档案卡片(每个机会一份)
│   ├── sources/         # 信息源档案
│   └── ACTION-PLAN.md   # 老板决策文档
├── workflows/           # 单个机会的端到端可执行工作区
│   └── <slug>/          # 与 docs/opportunities/<slug>.md 一一对应
├── AGENTS.md
├── LICENSE
└── README.md
```

### 2. `docs/` 与 `workflows/` 的边界

| 放哪里 | 内容 |
| --- | --- |
| `docs/rules/` | 跨工作流可复用的规则(评分、验证、自动化、合规、工作区结构本身) |
| `docs/opportunities/<slug>.md` | **机会档案卡片**:一句话定位、评分明细、风险摘要、参考来源 |
| `docs/sources/` | 信息源档案 |
| `docs/ACTION-PLAN.md` | 当前最该做哪一件的决策入口 |
| `workflows/<slug>/README.md` | 该机会的**执行入口**:目标、当前状态、下一步 |
| `workflows/<slug>/deploy/` | 部署代码与配置(Docker、脚本、`.env.example`) |
| `workflows/<slug>/ops/` | 日常运维:周报模板、事故 SOP、健康检查 |
| `workflows/<slug>/compliance/` | 风险登记册、ToS 摘要、应急话术 |
| `workflows/<slug>/pricing/` | 套餐表、落地页文案、Stripe 链接 |
| `workflows/<slug>/promotion/` | V2EX / TG / X / 小红书 推广文案 |
| `workflows/<slug>/data/` | 业务数据快照(默认 `.gitignore`) |
| `workflows/<slug>/docs/` | 项目内补充文档(不上升到全局规则的) |

### 3. 一一对应原则

- **每个 `docs/opportunities/<slug>.md` 必须有(且只能有)一个 `workflows/<slug>/`**。
- 反过来:每个 `workflows/<slug>/` 必须有对应机会档案,**禁止无 opportunity 的孤立 workflow**。
- 启动新机会的顺序:先写 `docs/opportunities/<slug>.md`(走完 5 个阶段) → 评分 ≥ 6 → 再建 `workflows/<slug>/`。

### 4. `workflows/<slug>/` 的标准布局(见 README.md)

```
workflows/<slug>/
├── README.md
├── CHANGELOG.md
├── deploy/
├── ops/
├── compliance/
├── pricing/
├── promotion/
├── data/    # .gitignore
└── docs/
```

历史项目(如 `llm-api-relay/`)沿用扁平结构,允许在 README 中说明差异,**不强制重排**。

### 5. 数据不入 git

`workflows/<slug>/data/` 默认加入仓库根 `.gitignore`,规则:

```
workflows/*/data/
```

业务数据快照如需留档,使用匿名化导出 + 单独 commit。

### 6. 索引同步

新增/修改工作区时,必须同步更新:

- `docs/opportunities/README.md`(机会档案索引)
- `workflows/README.md`(工作区索引)
- 涉及规则调整时同步 `docs/rules/README.md`
